# Enamel

The shared Enamelware rules come from the Enamelware handbook plugin (its skills decisions, product, design, development and operations); this file holds only what is specific to Enamel.

Read DESIGN.md before any interface work.

After any change to tokens/enamel.css, re-run the DESIGN.md script and rebuild the style guide pages in the same commit: `python3 tools/build_design_md.py`, then `python3 tools/build_styleguide.py`. The style guide copies its Rules section from DESIGN.md, so re-run it after rule changes too.

Open the style guide with the Enamel style guide launcher, a shortcut called "Enamel style guide" that runs `tools/serve.py`, never by double-clicking the html files. To check pages yourself, run `python3 tools/serve.py --no-open` and fetch over http.

docs/index.html, docs/components.html, docs/motion.html and docs/resize.html are fully generated by `tools/build_styleguide.py` (with `tools/components_page.py`, `tools/motion_page.py` and `tools/resize_page.py`); never edit them by hand. docs/overview.html is hand-written: never regenerate or restyle it, except its left menu between the enamel-menu markers, which the build script writes.

## Who uses this

- Kettle Video, the first app built on Enamel, uses an unmodified copy in its `vendor/enamel/` folder. Apps update by re-running their own sync script after a new VERSION here. The Kettle Video repo is read from here only through `scripts/peek.sh`. Never edit an app's files from here; if Kettle Video needs to change, say so in the issue comment and the report.
- Kettle Video keeps the old names (the "kt" prefix and the old file names) until its own switch issue, which follows MIGRATION.md. This repo's folder is called `enamel`; apps look for a folder called "enamel" first and fall back to the old folder name.
- Gaps found while building an app are fixed here, then the app re-syncs. Apps never style around a missing part: they add the gap to the standing issue "Gaps found by the apps" (#7, label `gaps`).

## How the work is done

The workflow is the handbook's (operations and decisions skills); Enamel's details are in `.claude/commands/` and `.claude/agents/`, and [docs/how-this-repo-is-built.md](docs/how-this-repo-is-built.md) explains it for visitors.

- Issues live in this repo and on the shared "Kettle" board (IDs in `.claude/board.json`). Board changes only through `scripts/board.sh`, which only reads, moves and labels this repo's cards, and closes the ones already in Done.
- Checks only through `scripts/test.sh`, in two modes: `scripts/test.sh` (quick) runs the unit tests, the build and structure checks, and the device's Firefox only on the style guide pages the change touches, in full and reduced motion; `scripts/test.sh full` runs everything, including the complete style guide check in Firefox.
- **Sizes** are the handbook's operations skill's. Here a screen is a component or a style guide page; the S limits also cover tokens, the style guide launcher and `tools/serve.py`; regenerated files are the ones the build scripts write; and the issues of a series share a `series: <name>` label.
- **Decide more, stop less.** "The design system" means this repo's own tokens and components; the details are in `.claude/commands/next.md`, "Decide or block".
  - A choice made without asking gets an issue comment "Decided: <what>. Why: <one line>. To change it, reply on this issue." and the `decided` label.
  - Hard stops, the only reasons to stop, are the handbook's (its decisions skill), plus: copying anything of Valve's; adding, renaming or removing a token, component class, state attribute or script function the issue doesn't ask for; anything that could change, move or delete files outside the repo, or that a git revert can't undo; security; the issue and CLAUDE.md contradicting each other.
  - Design system changes are expected: everything here that uses a changed size, colour or component follows, and that is in scope. Never hardcode a size a token provides: read the token or measure the element.
- Every change apps would notice bumps `VERSION` and adds a plain-language `CHANGELOG.md` entry, which says what apps must change for any rename or removal. Releasing and tagging: `.claude/commands/next.md`, steps 6 and 9.
- Idle work is paused: `/next all` stops when nothing is left to build, and test-writer and refactor-scout run only through `/tidy` (refactor-scout on Sonnet, or Opus with `/tidy deep`).
- When asked to continue or change #N, read that issue and its comments with `gh` first.
- The phrase "#N failed: <what happened>" (several issue numbers allowed) comments the feedback on the issue and moves it to More to do, without starting the fix.

## Hard rules

- Steam baseline values are recorded under Enamel's own names only. Nothing else comes from Valve or the Steam client, class names included.
- Case-study and portfolio material never goes in this repo; it is kept outside it.
- Scripts are kept in tools/; the workflow's small shell wrappers are in scripts/.
- Do not rename, add or remove tokens or rules unless asked. If one seems missing, say so in the report instead.
- Commit and push only as `/next` describes: issue branches and `main` on GitHub.
- No file names a capture size or a device as the source of a value; the rest of the layout rule is DESIGN.md Part 2.
- Verify your own work: the CSS parses; the page opens without errors; every token in enamel.css appears on the page and in DESIGN.md Part 1 with the same value; the page uses no colour that is not a token; running the DESIGN.md script twice changes nothing the second time.

## Public writing

Enamel is public and part of a design portfolio, so everything a visitor can read makes sense to a stranger: the README, docs/, DESIGN.md, DECISIONS.md, CHANGELOG.md, MIGRATION.md, the style guide, the workflow files in `.claude/`, issues and comments. Testing comments and reports follow it, and so do commit messages. Past commits are never rewritten. The handbook's product skill (principle 7) and decisions skill (the hard stop on private details) apply; here they also mean:

- **Project voice:** "Enamel uses…", "Chosen because…". Never "I", "we", "you", and never "owner" for the person who runs the project. Instructions addressed to Claude Code, in CLAUDE.md and `.claude/`, may speak to it as "you".
- **Devices** are named only as reference hardware: Steam Deck (SteamOS) and Retroid Pocket Nova (Armada).
- **Nothing private** also means no machine or login names, no email addresses (the commit address included), and no references to private chats, documents, design canvases, boards or repos. Those are described in words; links only go to public places. Example content is always invented.
- **Issues** use the headings in `.claude/commands/draft.md` (step 4); issues the workflow files by itself keep the headings their later steps read.
- Workflow terms are explained in [docs/how-this-repo-is-built.md](docs/how-this-repo-is-built.md); public text points there.
- **Checked automatically** by the public-text check in `tools/release_check.py` (part of the quick checks), in every published file, this one and `.claude/` included; the few lines that need a flagged text are listed in it with the reason. The reviewer checks every change against this section.
